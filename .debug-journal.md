## Hypotheses

1. [confirmed] Chromium caches a rejected dynamic import for the document lifetime. Evidence: after aborting the config chunk once and removing all routes, Retry issued no second request and the canvas timed out.
2. [refuted] The abort route remained active. Evidence: `page.unrouteAll()` completed before Retry and no second request reached routing.
3. [refuted] Retry selected the wrong factory. Evidence: the UI returned to loading and the retained-request unit contracts pass, but the module network request never occurred.

### Red phase (2026-09-08T21:10:00+09:00)

- Test: `e2e/app.spec.ts` - `reloads after the lazy game module request fails`
- Command: `bun run test:e2e -- --grep "reloads after the lazy game module request fails"`
- Output: Chromium reached `Unable to start the game.`, then timed out waiting for `getByRole('button', { name: 'Reload' })` at `e2e/app.spec.ts:61`.
- Confirms: the production-browser harness reproduces the misleading recovery action.

## Root cause

- Mechanism: the browser module map retains the rejected dynamic import, so invoking the same default loader after a network failure returns the cached rejection without a new request.
- Evidence: no config chunk request occurred after routes were removed and Retry was clicked; canvas wait timed out after 30 seconds.
- Fix scope: distinguish module-load recovery from factory recovery and use a document reload only for the former.
